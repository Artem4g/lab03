# lab03
1. Етапи build pipeline
- program.c -> gcc -E -> program.i: текстовий C-код після препроцесора (підставлено #include <stdio.h>, розкрито макроси), CPU виконати не може.
- program.i -> gcc -S -O0 -masm=intel -> program.s: текстовий Assembly (x86-64), містить мітки add, main та інструкції, але це ще не машинний код.
- program.s -> gcc -c -> program.o: бінарний relocatable ELF object file, містить машинний код та таблицю символів (nm program.o показує визначені символи main, add, global_value, global_empty і невизначений зовнішній символ printf).
- program.o -> gcc -> program: ELF executable, лінкер об'єднує об'єктні файли та підключає бібліотеки, файл можна запускати напряму.
- Перевірка memory_map.c:
  memory_map.c (C source, текст, CPU не виконує)
  memory_map.i (preprocessed C source, текст, CPU не виконує)
  memory_map.s (assembly, текст, CPU не виконує)
  memory_map.o (relocatable ELF object, бінарний код, CPU напряму як програму не запускає)
  memory_map (ELF executable, бінарний виконуваний файл, завантажується ОС і виконується CPU)

2. Linker error та виправлення
- При збірці лише main.o (gcc main.o -o app) виникає помилка undefined reference to calculate.
- Компіляція main.c у main.o проходить успішно, бо є прототип int calculate(int a, int b); і компілятор перевіряє лише типи.
- Лінкінг падає, бо реалізація calculate відсутня.
- Після створення calculate.c, компіляції в calculate.o і збірки gcc main.o calculate.o -o app помилка зникає, програма виводить 30.

3. Аналіз ELF (readelf -h program)
- Class: ELF64 (64-бітний формат ELF)
- Data: 2's complement, little endian
- Type: DYN (PIE executable) або EXEC
- Machine: Advanced Micro Devices X86-64 (архітектура x86-64)
- Entry point address: адреса входу в програму (стартовий код перед main)

4. Секції ELF (.text, .rodata, .data, .bss)
- .text: машинний код функцій (add, main, sample_function).
- .rodata: дані лише для читання, рядкові літерали та константи (наприклад, "Computer Systems", форматні рядки printf, "Hello ELF Memory").
- .data: ініціалізовані глобальні та static змінні з ненульовими значеннями (global_value = 10, initialized = 123, static_initialized = 456, global_init = 100, static_init = 200).
- .bss: неініціалізовані (або з нульовим значенням) глобальні та static змінні (global_empty, uninitialized, static_uninitialized, global_uninit, static_uninit).

5. Експеримент з великою .bss (sections.c)
- При заміні int uninitialized; на int large_array[100000]; розмір секції bss у виводі size sections зростає приблизно на 400 000 байт (100000 * 4 байти).
- Розмір самого виконуваного файлу (ls -lh sections) при цьому зростає значно менше або майже не змінюється, бо для .bss у файлі на диску не зберігаються нульові байти — пам'ять під цю секцію виділяє та заповнює нулями ОС під час запуску.

6. Динамічні бібліотеки (ldd program)
- ldd program показує залежність від стандартної бібліотеки C (наприклад, libc.so.6).
- Повна реалізація printf() не вшита в наш бінарник, а береться зі спільної бібліотеки.
- .so означає Shared Object (динамічна бібліотека).
- Декілька програм можуть використовувати одну shared library, щоб економити місце на диску та оперативну пам'ять: код бібліотеки не дублюється в кожному executable і може спільно використовуватися процесами в пам'яті.

7. Executable та process
- process як файл на диску — це статичний ELF-файл.
- PID (через ./process та ps -p PID) — це вже запущений процес у пам'яті зі своїм станом, адресами, дескрипторами та часом виконання.

8. Прогноз і результат розміщення змінних (memory.c та memory_map.c)
- Прогноз:
  main / sample_function -> code (.text)
  global_initialized / global_init, static_initialized / static_init -> data (.data)
  global_uninitialized / global_uninit, static_uninitialized / static_uninit -> bss (.bss)
  string literal -> rodata (.rodata)
  local / local_var -> stack
  dynamic / heap_var (malloc) -> heap
- Результат і групування адрес:
  Адреси код/константи/глобальні/статичні змінні знаходяться в зоні образу програми, heap — окремо, stack — окремо у верхній частині адресного простору.
  global_initialized і global_uninitialized лежать у різних секціях (.data і .bss), тому хоч і близько в межах сегмента даних, але в різних секціях.
  local не лежить поруч із глобальними змінними та не лежить поруч із malloc.
  При кожному запуску адреси змінюються через ASLR.

9. Концептуальна memory map (від вищих адрес до нижчих)
- Stack: local_var
- Heap: heap_var (malloc)
- .bss: global_uninit, static_uninit
- .data: global_init, static_init
- .rodata: str_literal
- .text: sample_function, main

10. Результати stack та heap експериментів
- stack.c: при вкладених викликах level1 -> level2 -> level3 адреси локальних змінних змінюються і на x86-64 ростуть у бік менших адрес (&c < &b < &a), оскільки стек росте вниз.
- heap.c: адреси a, b, c виділені через malloc належать до heap (а не stack); вони можуть бути поруч або з проміжками/вирівнюванням залежно від алокатора, тому послідовність адрес не варто вважати гарантованим правилом.

11. Відповіді на контрольні питання
1. Етапи збірки: preprocessing (.i), compilation (.s), assembly (.o), linking (executable).
2. Preprocessor обробляє директиви (#include, #define), видаляє коментарі й готує чистий C-код.
3. Compiler перекладає C-код в асемблерний код для цільової архітектури.
4. Assembler перетворює асемблерний код у машинний код в об'єктному файлі (.o).
5. Object file містить машинний код, секції даних/коду, таблицю символів і таблицю релокацій.
6. Linker поєднує об'єктні файли та бібліотеки, розв'язує посилання на символи й формує виконуваний файл.
7. undefined reference означає, що символ використовується, але його визначення не знайдено на етапі лінкування.
8. Symbol — це іменована сутність (функція або глобальна/статична змінна) з адресою або позначкою зовнішнього посилання.
9. Header file (.h) містить оголошення (прототипи, типи, макроси), а library містить скомпільований код реалізації функцій.
10. ELF (Executable and Linkable Format) — стандартний формат виконуваних, об'єктних і спільних бібліотечних файлів у Linux.
11. .text містить виконувані машинна інструкції програми.
12. .rodata містить дані лише для читання (рядкові літерали, константи).
13. .data зберігає ініціалізовані змінні з ненульовими значеннями, а .bss — неініціалізовані (або нульові) статичні/глобальні змінні.
14. Велика .bss не обов'язково сильно збільшує розмір файлу на диску, бо нульові байти .bss не записуються у файл і виділяються під час завантаження в пам'ять.
15. ldd показує динамічні спільні бібліотеки, від яких залежить виконуваний файл.
16. Executable — файл на диску, process — запущений екземпляр програми в пам'яті з власним станом і ресурсами.
17. Локальні змінні концептуально знаходяться на stack (у фреймі поточної функції).
18. Heap використовується для динамічного виділення пам'яті під час виконання програми (malloc/free).
19. Stack керується автоматично при викликах/виходах із функцій і зазвичай росте вниз, а heap керується вручну програмістом і має більший/гнучкіший час життя даних.
20. Адреси змінюються між запусками через ASLR (рандомізацію адресного простору) для підвищення безпеки.
21. Temporal locality — тенденція повторно звертатися до тих самих даних або інструкцій найближчим часом.
22. Spatial locality — тенденція звертатися до даних або інструкцій за сусідніми адресами.

12. Висновок
Пройдено повний шлях від вихідного коду на C через препроцесор, компілятор, асемблер і лінкер до ELF-файлу та процесу в пам'яті, досліджено секції, динамічне лінкування, роботу стеку і купи.
